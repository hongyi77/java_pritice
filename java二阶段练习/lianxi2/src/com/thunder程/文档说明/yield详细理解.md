# yield() 详细理解

## 一句话总结
> **yield() = "我先不跑了，让同级别的人先跑一步，我回到队尾重新排队"**

---

## 核心特点

| 特点 | 说明 |
|------|------|
| 是静态方法 | 用 `Thread.yield()` 调用 |
| 让出CPU | 当前线程从运行态 → 就绪态 |
| 不释放锁 | 如果持有锁，礼让后锁还在手里 |
| 只是提示 | JVM不保证一定让出，可能接着执行 |
| 同优先级 | 只有同优先级或更高优先级的线程才有意义 |

---

## 对比三兄弟：sleep / yield / join

| 方法 | 状态变化 | 释放锁？ | 是否强制 | 用途 |
|------|---------|---------|---------|------|
| `sleep(1000)` | 运行 → 计时等待 | ❌ 不释放 | ✅ 强制睡 | 暂停一段时间 |
| `yield()` | 运行 → 就绪 | ❌ 不释放 | ❌ 只是提示 | 主动让出CPU |
| `join()` | 当前线程阻塞 | ❌ 不释放 | ✅ 强制等 | 等别人跑完 |

---

## 常见误区

### 误区1：yield() 会让线程停止执行
**错！** yield() 只是让线程回到"就绪队列"，等着被重新调度，不是停止。

### 误区2：调用 yield() 后一定能被其他线程抢到CPU
**错！** 调度器可能还是调度当前线程继续执行。

### 误区3：yield() 能降低线程优先级
**错！** 它只是让出当前这一次执行机会，不影响优先级设置。

---

## 什么时候用 yield()？

实际开发中**很少直接用 yield()**，原因是：
1. 它只是"提示"，不可靠
2. 现代CPU速度太快，手动礼让意义不大

**更推荐的做法：**
- 需要暂停 → 用 `sleep()`
- 需要等别人 → 用 `join()`
- 需要线程安全 → 用 `synchronized` 或 `ReentrantLock`

---

## 实验结论

运行 `YieldDemo.java` 后可以发现：
- yield 之后，**有时**是其他线程先执行（效果出来了）
- **有时**还是当前线程接着执行（yield没效果）
- 这就是"提示"的含义：说了但不保证听

> 如果真的想用，唯一有意义的场景
CPU密集型任务不想独占CPU —— 比如一个后台计算的线程，想让UI线程不被卡住：

Thread worker = new Thread(() -> {
for (int i = 0; i < 1000000; i++) {
// 每次循环后提示"让别人也有机会"
Thread.yield();
doSomething(i);
}
});
但这种情况，更好的做法是用 sleep(0) 或者直接交给线程池管理，而不是 yield()。

暂停一下	sleep()

线程池管理	ExecutorService
